## 二、最優先處理的三件事

### 1. 修正 `RealIP` 的代理信任邊界

**已確認：** [internal/auth/ip.go](../../internal/auth/ip.go) 依序直接採用 `CF-Connecting-IP`、`X-Forwarded-For` 第一個條目，最後才使用直連 IP，沒有先驗證請求是否來自可信代理。

這個值被用於 Web 登入／存取的 IP 限制，以及依 IP 計算的速率限制與分享 PIN 嘗試計數。如果外部請求能直接到達應用程式，或代理未正確清理使用者提供的標頭，來源判斷就可能被偽造。

**影響界線：** 繞過 IP 限制不等於繞過 Web 密碼、session token、Telegram 身分驗證或 MCP token。現行 Web 驗證流程仍會檢查密碼或有效 token；不能把這項問題寫成「只改標頭就取得所有操作權」。

**建議：**

- 預設採用直連來源，只有明確列入可信代理清單的來源可以提供轉發資訊。
- 不把所有本機或私有網段來源一概當作可信代理。
- 定義代理如何覆寫標頭、各標頭優先順序，以及多層代理的解析規則。
- 測試直連偽造標頭、不可信代理、可信代理、無效 IP 與多層代理情境。

**相關實作：** [server.go](../../internal/server/server.go)、[ratelimit.go](../../internal/api/ratelimit.go)、[share.go](../../internal/api/share.go)。

### 2. 將 agent 圖片移出公開靜態出口

**已確認：** [SaveBase64Image](../../internal/media/save.go) 仍將圖片寫入 `internal/static/uploads`，回傳 `/uploads/<filename>`；[server.go](../../internal/server/server.go) 的公開 `app.Static` 提供這個目錄，不要求登入。

**需區分的兩條路徑：**

- 使用者上傳的附件：已存入 `workspace/uploads`，透過有驗證的 session 附件路由讀取。
- agent 產生的圖片：仍走公開靜態目錄，本項問題指的是這條路徑。

**風險界線：** 圖片檔名由 `crypto/rand` 產生 16 bytes 隨機值，也就是 128 位元隨機值，不是容易猜中的流水號。問題是持有 URL 者可免登入讀取，且該 URL 不受 session 分享撤銷／到期的授權檢查約束。

**建議：**

- 將圖片存到公開靜態根目錄之外，建立圖片與 session 的關聯。
- 讀取時檢查擁有者身分或分享的角色、範圍與有效期限。
- 一併處理歷史訊息的既有圖片 URL；只改新圖片存放位置不會關閉舊出口。
- 測試未登入、不同 session 訪客、有效分享、到期／撤銷分享及歷史圖片。

### 3. 讓「允許此操作」與實際放行範圍一致

**已確認：** [ChatView.js](../../internal/static/js/chat/ChatView.js) 的 `handleAllowOnce` 傳送工具名稱；[handler.go](../../internal/ws/handler.go) 的舊 Claude denial 重跑分支把工具清單傳給 `runAgent`；[runner.go](../../internal/claude/runner.go) 再產生 `--allowedTools` 參數。

例如對 Bash 按「允許此操作」，舊重跑流程傳入的是 `--allowedTools Bash`，沒有把許可限定到畫面上那一條命令。這會放寬該次重跑的工具授權；其他既有規則仍可能拒絕操作，不能解讀成所有限制都被移除。

**影響界線：** 這是舊 denial 重跑路徑的問題。新的 prompt-tool 請求會先由 `permResolve` 處理，不應把兩種流程混為一談。本次確認的是程式碼傳遞的授權範圍，未重新執行真實 CLI 的多命令驗證。

**建議：**

- 優先將授權綁定到實際待核准請求；若仍需工具層級放行，介面明確說明「本次重跑允許此工具」。
- 分別測試新 prompt-tool 與舊 denial 重跑流程。
- 驗證允許後的其他命令是否仍需授權，以及拒絕、中斷、多人回應後是否留下待處理狀態。

## 五、前版報告的更正

### editor 是高權限角色，不直接判定為越權漏洞

[共享設計](../plan/done/share-chat.md) 明確定義 editor 與擁有者具有同等操作權限，包括回應授權、Shell、切換模型與權限模式；目前 README／功能說明也將 editor 描述為 full-access。

因此，editor 能核准授權或操作 Shell 符合目前角色設計。若希望增加「只能協作聊天」的角色，那是新的產品需求，不能直接把既有行為定性為越權並刪除其權限。

這也不表示共享功能的每個隔離與撤銷情境都已通過實機驗證；本次僅更正角色語意的判斷。

### 不把整段對話視為必然傳送到 Telegram

使用 Telegram WebView 不足以證明完整工作對話會送進 Bot 訊息。應依實際資料流判斷。

[通知實作](../../internal/tg/alert.go) 可在錯誤通知中包含 prompt 摘要與錯誤摘要；`notify.include_prompt` 的預設值是 `true`。工作資料的通知需求應針對這些實際欄位評估，不能把未確認的公司政策寫成已存在的違規問題。關閉 prompt 摘要也不代表其他通知欄位一定不含敏感內容。

### 不把 CSS 出現次數當成已確認的體驗缺陷數量

介面存在 10px／11px 小字與 `maximum-scale=1.0`，但先前的「55 處」只是搜尋數量，未逐項驗證是否顯示、是否關鍵或是否難讀。本報告不以該數字代表已確認的缺陷數量，也不宣稱所有瀏覽器都會禁止縮放。
