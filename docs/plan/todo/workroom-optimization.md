# 工作室首次運行後優化計畫

日期：2026-11-18。狀態：設計草案，尚未開始本計畫的產品實作。

依據：[首次運行觀察](../../reviews/2026-11-18-workroom-first-run-observations.md)。
畫面稿：[工作室版面預覽](workroom-optimization-preview.html)（獨立 HTML、示意資料、不連正式服務）。

## 1. 目標與範圍

進入工作室後，使用者應能在第一屏辨認現任 PM、目前派工、需要自己處理的事項，以及訊息真正的發送者。手機應能完成相同操作，不必跳回各 session 才能授權或回答。

本輪交付計畫與畫面稿；不改產品程式、不派工、不操作正式工作室、不重啟、不提交。後續實作沿用現有 Go／React／語意色票，不加入 UI 套件或額外模型摘要服務。

MCP 保留通訊與工具能力；PM 等待、結束回合、是否回覆通知，由 supervisor skill 與使用者指示決定。不得以本計畫為由加入 MCP 強制結束回合、攔截工具或自動中斷驗收。

## 2. 先分清楚已做與待做

| 項目 | 規劃時的已知狀態 | 本計畫處理方式 |
|---|---|---|
| 整框點擊、PM 最左 | 上一輪已有工作樹修正及獨立 EXE，正式服務尚未載入 | 先驗收既有修改，不重寫 |
| 額度停止後交接待處理輸入、附件及回報 | 上一輪有 DB／API／附件回歸；正式環境未重新驗交接 | 補完整操作驗收與清楚的交接狀態 |
| 工作室內授權／選擇 | 已有共用 SessionActionCards、桌面／手機 fixture | 補提醒、長內容、多人競答、斷線與真實環境驗收 |
| MCP 諮詢信封 | 另有並行修改，來源身分在時間軸的問題仍需獨立核對 | 調整前重讀最新 diff，不覆蓋其他人的成果 |
| quota-auto-resume | 另一工作室持續實作 | 只整合它已提供的狀態，不重做其判定、輪詢或排程 |

每階段開始先保存比較基準與檔案歸屬，查明測試中的 binary／前端版本。未載入的修正不能列為新 bug；未實際驗過的環境不能標已完成。

## 3. 畫面設計

### 3.1 視覺方向

沿用 MiniApp 的紫色操作重點與深／淺色系統。工作室是一張工作桌：對話居中、派工在旁、決策有明確來源。邊框只區分成員、待處理事項和輸入區，正文以留白分隔，避免每句訊息都做成卡片。

| 設計項 | 建議規則 |
|---|---|
| 色票 | 使用 `ra-bg`、`ra-card`、`ra-line`、`ra-t1/t3`、`ra-accent`、`ra-warn` 等既有 token；不在產品硬寫新主題 |
| 畫面稿參考色 | 深底 #10131C、表面 #191E2B、正文 #E9ECF5、次要 #AFB8CE、操作 #B9AAFF、提醒 #FFD18A；只供草案預覽 |
| 字體 | 沿用系統繁中字體，不下載字型；標題 18px、正文 14–16px／行高 1.65、狀態 12–13px；ID／命令才用等寬字 |
| 間距 | 4／8／12／16／24px；主要觸控目標至少 44 × 44px；不靠細小圓點當唯一狀態 |
| 背景 | 保留個人背景設定；標頭、輸入框、工作面板使用不透明語意表面，對話正文落在有足夠遮罩的閱讀區 |
| 對齊 | 名稱、正文、派工一律靠左；只有使用者本人的輸入靠右；PM 依資料順序排首位，DOM 與鍵盤順序相同 |

草案取捨：不新增統計儀表板、花俏動畫或第三條常駐工具列。視覺重點放在「待你處理」及工作來源，整體保持與現有應用一致。

### 3.2 寬版：工作室可用寬度 ≥ 960px

以工作室容器寬度判斷，不以整個螢幕寬度判斷；全域 session 側欄沿用既有行為。

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回  quota-auto-resume            待你處理 1   工作室設定     │
├──────────────────────────────────────────────────────────────┤
│ [現任 PM：名稱／狀態] [執行者／狀態] [舊 PM／已暫停] …        │
├───────────────────────────────────┬──────────────────────────┤
│ 對話                              │ [派工] [備忘]            │
│ PM → 執行者  派工 #6              │ 執行中                   │
│ …                                 │ #6 額度判定  miniapp…    │
│ 執行者 → PM  回報                  │ 需要處理／暫停原因       │
│ …                                 │ 已結束（可收合）         │
│ [具名授權／問答卡片，按需顯示]     │                          │
├───────────────────────────────────┤ 備忘全文在「備忘」切換   │
│ 傳給 現任 PM  · 執行中，將排隊     │ 後顯示，不擋派工         │
│ [附件] [輸入訊息………………] [送出]   │                          │
└───────────────────────────────────┴──────────────────────────┘
```

- 主區使用 `minmax(0, 1fr)`，面板 280–340px；正文限制約 72ch。面板預設開「派工」，進行中／需處理排前，歷史完成紀錄預設收合。
- 外殼受現有 h-app／WebView 可用高度約束，採 `auto minmax(0,1fr)` 等列配置，逐層設 `min-height:0`。時間軸與側面板各自捲動，外層不能再長出第三條捲軸；不以 body overflow 裁切掩蓋問題。
- 標頭與輸入區在布局列內，避免覆蓋正文。多行輸入設上限後才在輸入框內捲動，不讓工具列把整張工作桌擠掉。

### 3.3 窄版：工作室可用寬度 < 960px

```text
┌────────────────────────────┐
│ 返回  工作室名稱   工作概況 │
│ [現任 PM／執行中] [成員 3]  │
├────────────────────────────┤
│ [待你處理 1・查看]           │ ← 僅有待處理時出現
│ 對話／派工與回報            │
│ …                          │
│ [具名授權／選項]            │
├────────────────────────────┤
│ 傳給 現任 PM · 將排隊       │
│ [附件] [訊息……] [送出]      │
└────────────────────────────┘
```

- 手機只保留現任 PM 摘要及「成員 N」入口；完整成員、額度與錯誤詳情在工作概況內，避免三張長卡把第一屏擠滿。
- 「工作概況」在原工作室內切換為全寬工作面板；提供清楚「回到對話」。保留草稿、對話捲動與目前閱讀位置，不開第二個工作室或額外全頁導覽。
- 「派工／備忘／成員」用原生按鈕切換並標示選中狀態；若採 ARIA tabs，必須另外實作完整方向鍵規則，首版不必自製 tabs widget。
- 使用現有 TG safe area、鍵盤高度與輸入框規則。320px、390px 及鍵盤開啟時，按鈕不能被裁掉；200% 文字縮放後允許換行，不強迫固定標頭高度。

## 4. 顯示與互動規則

### 4.1 發送者、收件者與長文

1. 只有真實使用者輸入標「你」並靠右。PM 派工、執行者回報、跨 session 訊息靠左，明列名稱與收件者；跨工作室標示來源工作室（資料可信且可用時）。
2. 新訊息優先持久化結構化來源及關聯 job／room；API 欄位在實作前確認，不能只把諮詢信封改短就宣稱解決身分問題。歷史列有可信 metadata 才回填顯示；無法辨識的舊資料標「來源未辨識」，不偽裝成人類。
3. 預覽先顯示正文前 2–3 行。工作目錄、from/to session ID、hop、通訊說明放「傳遞資訊」原生 details；完整原文可展開、複製，不刪除 DB 中的歷史資料。
4. 不把任意使用者貼上的「from_session_id」當作可信來源；舊信封解析只能作顯示輔助，不能用於授權、資料存取或真正的訊息路由。
5. 預設保留所有訊息。首版不自動去重或隱藏「收到」，避免把有意義的確認吃掉；長通知可收合。減少不必要的通知回覆另由 skill 約定，不改 MCP 限制。

### 4.2 成員、額度與佇列

| 情境 | 顯示 | 操作／限制 |
|---|---|---|
| 正在執行 | 執行中＋已知開始時間；可得時顯示一行最新活動 | 不把文字省略動畫當成唯一進度 |
| 閒置 | 閒置 | 不自行推論為「正在等執行者」 |
| 閒置且佇列暫停 | 佇列已暫停＋原因，另顯示佇列數 | 0 則也顯示暫停，不能偽裝正常閒置 |
| 有待授權／回答 | 待你授權／待你回答 | 工作室內定位對應卡片 |
| 已有可靠額度停止原因 | 額度不足／額度守門＋重置時間（若有） | 僅 100% 快照不足以判定本次停止原因 |
| 額度快取過期／未知 | 過期／尚無資料＋更新時間 | 不把快取當即時值或拿它禁止交接 |
| 讀取失敗／斷線 | 狀態未更新＋最後成功時間／重試 | 保留上次資料但明示舊快照 |

- 額度是 provider／帳戶快取，不是該成員本身的消耗。摘要顯示最大已用視窗，詳情保留所有視窗及重置時間。
- 成員端點以最小欄位補足 queue_length、queue_paused、失敗原因與時間、狀態新鮮度。具體取值須沿用後端可靠資料，避免前端以錯誤字串或名稱決定業務狀態。
- 同時有多個狀態時：先顯示待授權／問答等可操作事項，其次失敗／暫停，再顯示執行狀態；其他訊息在詳情保留。
- 編輯工作室的現任 PM 不因名稱包含「PM」而改判；以 room.pm_id／role 為準，不自動改名舊 session。

### 4.3 授權與選擇

- 卡片留在時間軸，標示成員、工具／問題、作用範圍及重試是否會重跑。頂部僅顯示一個「待你處理 N」定位入口，不疊多張固定橫幅。
- 閱讀舊訊息時不自動拉到底、不搶焦點；使用者點定位後才捲到卡片。不同成員可同時待處理，必須分開提交。
- 允許、拒絕、回答只針對當前 session／request；連線中斷不可假裝送達，失敗保留卡片與已填答案；重新整理可恢復後端仍有效的請求。
- 多裝置競答以伺服器原子處理結果為準，過期請求不能再次執行。僅在真正的安全取捨需要時確認，不額外加入每次都確認的彈窗。
- 沿用共用 SessionActionCards；不建立第二套授權 API 或把工作室訪客權限擴大。

### 4.4 派工、備忘、交接

- 派工先顯示進行中／需處理，再顯示已結束。每列至少有 #ID、執行者、狀態；已有可信資料才顯示任務主旨、開始／更新時間，不從備忘猜出完成百分比。
- 備忘仍是完整 Markdown，使用原生 details 展開次要長段落；首版不新建平行摘要欄位或自動改寫 PM 備忘。
- 交接在既有「編輯／交接 PM」完成。顯示現任與接任、要移交的群聊佇列／回報數；不能要求沒額度的舊 PM 再跑一輪才能交接。
- 舊 PM 真正執行中／有未解授權時，說明需要先處理的原因；不默默強殺。舊 PM 閒置且因額度停止時可移交；新 PM 自身的額度、暫停及私人佇列保持原有狀態，不宣稱交接保證立即開工。
- 成功後更新角色、輸入目標與成員排序。草稿保留，舊 PM ID 的尚未接受輸入遇到衝突時提示確認，不靜默轉送到另一位 PM。歷史收件者不能隨現任 PM 改變。
- 交接紀錄應可辨識為系統事件；保留既有備忘、派工、附件與訊息去重。具體新增事件格式待實作階段確認。

## 5. 實作順序與影響範圍

| 階段 | 工作 | 主要檔案／區域 | 完成門檻 |
|---|---|---|---|
| A：基準與既有修正驗收 | 固定本輪 scope；整合上一輪改動；查核正式／測試 binary 差異 | 現有 diff、測試、執行環境 | 版本與驗收證據可追溯，不覆蓋並行修改 |
| B：來源與狀態正確性 | 發送者 metadata、舊資料降級、暫停／佇列／錯誤快照、交接提示 | db/room_timeline、api/rooms、MCP 寫入來源接點、hooks/rooms | 不再把代理訊息標「你」；額度停止不被顯示成正常閒置 |
| C：版面與閱讀 | 主副欄、手機概況切換、派工先行、背景閱讀表面、長文 disclosure | RoomView、RoomControls、RoomMessageBubble、RoomsSection、index.html | 長備忘不擋派工，沒有第三條外層捲軸，320px 可操作 |
| D：待處理與活動 | 具名卡片定位、斷線／競答／重整、最小活動資訊 | SessionActionCards、useChatSocket、工作室狀態資料 | 不重複授權、不遺失答案、不為所有成員載入整段聊天歷史 |
| E：實際試跑 | 用完整新版在允許的更新時機驗收，觀察後補缺陷紀錄 | 瀏覽器／Wails／TG | 已驗與未驗分列；通過後才更新完成狀態 |

先 B 再 C，避免只做漂亮版面卻仍顯示錯誤身分。C、D 以目前共用元件整合；不為了並行而讓多人同時改 RoomControls／index.html。這份計畫不自動啟動執行者。

活動資料首選現有通道與有界快照；實作前核對 WS 連線是否會載入歷史、標已讀、刷新額度或喚醒任務。首版沒有可靠活動來源時顯示「執行中，活動資料未提供」，不新增所有成員常駐 WS 或高頻輪詢。

## 6. 驗收清單

2026-11-18：首版程式已完成並整合；Go、前端與隔離產品瀏覽器驗證通過，詳見 [驗收紀錄](../../reviews/2026-11-18-workroom-optimization-verification.md)。以下保留完整實機驗收清單，Wails／Telegram／真實額度停止操作未驗，不整批勾選。

- [ ] 身分：本人輸入、PM 派工、worker 回報、跨工作室訊息、無 metadata 的歷史資料皆有對應 fixture；含偽造信封的普通輸入。
- [ ] 狀態：idle／running／暫停且 queue=0／暫停且 queue>0／待授權／待回答／舊錯誤已恢復／快取過期／讀取失敗都有可辨識畫面。
- [ ] 版面：容器 1280、996、960、768、390、320px；長名稱、50 位成員、10,000 字備忘；桌面 200% 縮放、低高度與手機鍵盤，控制項仍可達。
- [ ] 閱讀：自訂高反差背景及深淺色；正文一般文字對比至少 4.5:1；派工第一屏可見；鍵盤可展開全文與傳遞資訊、可回對話，焦點順序與顯示順序一致。
- [ ] 捲動：頂部載入更早、長文展開、圖片晚載、備忘切換、新訊息及待處理出現時，閱讀舊訊息的錨點穩定；停底部時才自動跟隨。
- [ ] 決策：PM 與兩位 worker 同時請求，允許／拒絕／單選／複選／自由輸入均送對人；同步連點、斷線重連、重整及雙裝置競答不重複執行。
- [ ] 交接：舊 PM 額度停止＋待處理附件／回報＋私人佇列；新 PM 已暫停／沒額度；交接失敗回滾；輸入送出與交接競爭；歷史路由與去重保留。
- [ ] 程式檢查：相關 Go 套件、build／vet、internal/arch、frontend-layering、rooms 與共用授權回歸；只因實際改動或失敗擴大測試。
- [ ] 實機：Wails、一般瀏覽器、Telegram Android／iOS 分列結果；fixture 通過不算真實 provider／TG 驗收。

## 7. 首版不做與後續決策

不新增 AI 摘要、工作室儀表板、拖拉版面、智慧去重、跨 room 全域搜尋、工作室自動排程或新的授權框架。先讓現有工作室可讀、可判斷、可操作。

建議預設採本稿：派工優先、備忘切換、窄版收成員、保持所有訊息可讀。尚待實機確認的是 960px 分界與面板寬度；以 996px 真實長文場景和手機鍵盤結果調整，不先做成使用者設定。

畫面稿中的名稱、時間、#6 與額度均是示意快照，按鈕只改畫面，不連正式 DB／MCP，不代表這些狀態目前仍成立。
