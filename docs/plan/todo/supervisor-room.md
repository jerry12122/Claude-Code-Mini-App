# 功能計劃：Supervisor 工作室（虛擬群組 + 共享脈絡 + 額度守門）

> 狀態：第一期已試跑（2026-11-18，見第 6 節）；額度硬守門已實作並驗證（2026-11-18，見 7.2）；第二期（唯讀虛擬群聊檢視）已批准、尚未開工（見 7.1）；第三期尚未實作
> 建立日期：2026-11-17
> 目標：把「使用者 + PM（supervisor）+ 執行者」放進同一個虛擬群組，一個畫面看全局、共用脈絡、額度有守門。底層每個成員仍是各自獨立的 session／CLI 程序，不新增執行引擎。
> 靈感：Chief（AI 代理管理工具）的「共享脈絡」「待辦佇列」「用量上限」。只借設計，不整合、不安裝。

## 1. 為什麼不是「真群聊」

真群聊（每則訊息廣播給所有人、每個人都可能回）有三個問題，已在 `supervisor-workflow` §5.0 踩過：
- 互相回覆形成迴圈，靠 hop 上限硬擋。
- 每則廣播讓每位執行者各讀一次，token 成本隨人數倍增。
- 逼近 Roadmap「明確不做：DAG 編排引擎」。

所以採「**群組是檢視 + 路由規則**」：全部訊息顯示在同一條時間軸，但**只有被 @ 的成員會被觸發**。沒被點名的成員不跑、不耗 token，也不會形成迴圈。

## 2. 分期

### 2.1 第一期：零程式碼（只改 supervisor 流程文件）
- **額度守門**：派工前呼叫 `get_quota`，低於門檻就問使用者或換執行者。門檻由 PM 判斷、不設硬數字（約 70% 提醒、約 90% 以上不派；各 provider 額度單位不同，細節在 supervisor skill）。
  - 這只是軟性提醒：`get_quota` 回傳快取、不會刷新（`internal/quota/service.go`），`stale: true` 或無資料時必須視為「未知」而非充足；也擋不到已在佇列中、稍後才啟動的訊息。三期要做硬守門，必須在「訊息實際啟動」處檢查，不能只擋群組入口。
- **待決策 session**：固定一個 session，supervisor 要問人時用 `post_message`（`notify: true`）寫進去，未讀徽章當**提醒**。不觸發 agent、不耗 token。
  - 限制：徽章只計「非 pending、非 user、未讀」訊息（`internal/db/session.go`），聚焦並捲到底或全部已讀就清除，**不代表決策已完成**。`notify` 需要 `bot_token`，且忽略通知錯誤。要真的追蹤決策狀態，得另外做（例如帶完成狀態的待辦資料），不列入第一期。
- **共享脈絡檔 `context.md`**：目標、已決定事項、踩過的坑。派工模板加兩句：開工先讀、收工由 supervisor 追加新決策。
  - **位置（2026-11-18 使用者決定）**：脈絡含敏感資料，放 runtime 目錄、該群組專屬的 workspace，不放專案 repo。第一期還沒有群組實體，先由 supervisor 手動建一個固定資料夾，路徑記在任務輸入；第三期群組出現後改由群組擁有該資料夾。
  - 各 provider 讀取（唯讀）已於 2026-11-18 驗證通過，見第 6 節；寫入未測。

完成標準：用 2～3 個實際任務試跑，執行者確實讀寫 `context.md`，且待決策 session 的徽章能正常提示。

### 2.2 第二期：群組檢視（唯讀）
- 新增 `rooms(id, name)` 與 `room_members(room_id, session_id, role)`，role 為 `pm`／`worker`。
- 前端：一條合併時間軸，依時間混排成員訊息，氣泡署名沿用 `post_message` 的 `author`。
- 資料來源：**既有 MCP 查詢不夠直接用**（codex 對照程式碼的結論）。`get_messages` 有 `after_id` 但輸出缺 `author`；`list_activity` 無成員篩選、無游標且會截斷全文（`internal/mcp/tools.go`）。需要新增 room 專用查詢，帶「時間 + id」游標；訊息儲存仍沿用既有表，不新增。索引先用既有 `session_id`／`id`，是否新增以 `EXPLAIN` 決定。
- pending 訊息（串流中）要用原 id 更新，不能當新訊息重複插入。
- 標頭顯示各成員狀態與用量（沿用 `quota-usage-bars`）。

完成標準：同一畫面看得到 PM 與所有執行者的進度，不必切換 session；不改動任何成員的執行行為。

### 2.3 第三期：群組內路由與共享脈絡
- 在群組輸入框發訊息：預設只送 PM；有 `@成員` 才送該成員。
  - **現況落差**：`MentionMenu.js` 的 `@` 只是在 prompt 前置提示，由當前 agent 自己決定要不要呼叫 MCP，並不是由伺服器路由。群組路由需新增「明確收件者」欄位，由後端直接投遞。
- hop 防護有兩個已知缺口，群組不能只靠它擋迴圈：
  - hop 由「發送者最新 user 訊息文字」推算，引用 `hop:` 字樣也會被算進去。
  - 呼叫 `send_message` 時省略 `from_session_id` 會直接略過 hop 檢查（`prepareConsult`）。
  - 因此群組要在後端自己記路由深度，或在群組內的投遞一律強制帶 `from_session_id`。
- 群組層級共享脈絡：群組釘選一份 `context.md`，派工時自動帶路徑。
- 額度守門內建化：群組內成員低於門檻時，PM 的派工動作先被擋下並提示（對應 Roadmap Phase 3「額度將盡建議換手」、Phase 4「額度低於門檻自動暫停」）。

完成標準：未被 @ 的成員在整段對話中零新增執行；整條時間軸的 hop 不超過上限。

## 4. 明確不做
- 廣播式群聊（所有成員自動收到所有訊息）。
- 成員之間自動辯論／多輪自主協商；若出現「兩個執行者必須直接對話」的真實案例再評估。
- 自動拆任務的編排引擎（目標 → 任務圖）；規劃仍由 PM（supervisor）負責。

## 5. 風險
- 合併時間軸若直接掃多個 session 的完整歷史會很重，需分頁／`since`。
- PM 本身也是一個耗額度的 session，群組內多一層中繼會增加 token；第一期先量測再決定是否值得進第二期。

### 7.1 第二期：唯讀虛擬群聊（工作室檢視）

目標：把 PM 與執行者的 session 放進同一個「工作室」，用一條合併時間軸直接看到全局。**不新增執行行為**：不觸發任何成員、不改變路由；要指示成員仍進入該成員自己的 session（第三期才做群組輸入與 @ 路由）。

資料與 API（僅擁有者；訪客不在放行清單內預設 403）：
- 資料表：`rooms(id, name, created_at)`、`room_members(room_id, session_id, role, position)`，role 為 `pm`／`worker`。刪除工作室不刪 session；刪除 session 要同時移除其成員身分。遷移方式照 `internal/db` 既有慣例。
- `GET /rooms`、`POST /rooms`（name、members）、`PUT /rooms/:id`（改名、增減成員與角色）、`DELETE /rooms/:id`。
- `GET /rooms/:id`：成員清單，含各成員 session 名稱、agent 類型、狀態，以及該 provider 的額度摘要（沿用 quota 快取，`stale` 要標示）。
- `GET /rooms/:id/timeline?before=&limit=`：把所有成員 session 的訊息依「時間 + id」穩定排序合併，游標分頁；每筆帶 `session_id`、`session_name`、成員角色、agent 類型、訊息 `id`、role、`author`、文字、時間。只含使用者／助理／系統的文字訊息，不含工具呼叫細節。
- 串流中（pending）的訊息以**原訊息 id** 更新，前端以 id 去重，不可重複插入。

前端：
- session 列表新增「工作室」區塊與「新增工作室」對話框（名稱 + 選既有 session + 指定 PM）。
- 工作室畫面：標頭顯示成員晶片（狀態點 + 用量，點擊進入該成員 session）；主體是合併時間軸，每則氣泡標註來源成員（名稱與 agent 類型）；底部固定一行說明「唯讀：要指示成員請進入該成員的 session」，**沒有輸入框**。
- 更新方式：可見時每 3 秒輪詢最新一頁並以 id 合併，離開即停；本期不新增 WebSocket 協定。
- 往上捲載入更早訊息（`before` 游標）。

選做（不增加複雜度才做）：MCP `create_room`／`list_rooms`，讓 supervisor 派工時自動建立工作室。

完成標準：
- 單元／整合測試：合併排序穩定（同時間以 id 決勝）、游標分頁不漏不重、pending 以原 id 更新、成員 session 被刪除後時間軸不壞、未登入 401、訪客 403、不存在的工作室 404。
- `go build`／`go vet`／`go test`（排除 `poc/`）、`go test ./internal/arch/`、`node scripts/frontend-layering.test.cjs` 全過。
- 用臨時實例實測：建工作室、兩個以上成員的訊息混排正確、成員晶片可跳轉、離開畫面後不再輪詢。

### 7.2 額度硬守門（最小範圍）

只補第 6 節記下的缺口：「排隊中的訊息稍後自動啟動時不會被擋」。
- **觸發點**：伺服器要自動啟動佇列中的下一則訊息時。使用者在閒置 session 直接送出的訊息不擋（那是明確的人為動作）。
- **規則**：取該 provider 的額度快取；若不是 `stale`，且任一個有 `percent` 的視窗已用 ≥ 門檻（預設 90），就不啟動，改把佇列暫停（沿用既有 `queue_paused`），並讓使用者看得到原因（畫面提示，`notify` 通知設定開啟時一併推播）。使用者按「繼續」即可解除暫停。
- **失效時放行（fail-open）**：快取 `stale` 或沒資料時不擋，因為伺服器無法詢問使用者，擋下會比放行更糟。
- 沒有 `percent` 的視窗（例如 cursor 的 plan spend：`limit`／`used` 為金額）不參與判斷，避免像現在 cursor 的 33.75／20 美元那樣讓佇列永遠被擋。
- **設定**：`quota_guard_percent`，預設 90，設 0 停用。這是唯一新增的設定鍵，且非必填。
- 完成標準：單元測試涵蓋「超過門檻暫停且佇列內容保留」「低於門檻照常啟動」「stale 與無資料放行」「無 percent 視窗忽略」「門檻 0 停用」「使用者直接送出不受影響」；`go test`（排除 `poc/`）與 `go test ./internal/arch/` 通過。

#### 7.2 實作與驗證紀錄（2026-11-18）

- 實作者：cursor · Claude Sonnet 5.5 High（依 `docs/reviews/agent-ratings/` 的評價挑選）；supervisor 獨立驗收。守門在 `internal/ws/quota_guard.go`，掛在伺服器自動啟動佇列的入口 `Drain()`；任務收尾、重連、授權解除都會經過它。
- 單元測試涵蓋規格六種情境，另加「剛好等於門檻就擋」「使用者按『繼續』不被擋回」與「暫停後會廣播佇列狀態」。排除 `poc` 的 build／vet／全部測試、`go test ./internal/arch/`、前端分層檢查皆通過。
- **即時驗證**（臨時實例，門檻設 1，真實 claude 額度 51%）：第一則執行中排入第二則，收尾後佇列暫停，畫面顯示「佇列已暫停（1）」與「繼續」，session 錯誤文字為「額度守門：Current session 已用 51%，達到門檻 1%，佇列已暫停（按『繼續』可解除）」；按「繼續」後第二則正常執行。
- 規格外的決定（執行者）：按「繼續」一律放行，否則額度仍高時按了會立刻被再暫停；這是合理的，已保留。
- **已知限制**：
  - 沒有推播：暫停只在畫面上提示，沒人看畫面時只會發現佇列停住。要加 Telegram 通知得另外做。
  - 原因文字存在 session 的錯誤欄位並以 error 事件廣播，但聊天畫面上的暫停橫幅本身不顯示原因，原因要靠當下的提示或會話列表。
  - 任一個有 percent 的視窗達門檻就擋，對 Antigravity 這種有多個模型家族視窗的 provider 偏保守（例如 Claude/GPT 視窗滿了，也會擋用 Gemini 的排隊訊息）。
  - 只讀額度快取；快取過期時放行（fail-open）。
  - 實作花費：cursor plan spend 增加約 0.68 美元（33.75 到 34.43）。
